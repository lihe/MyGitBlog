# [什么是 Reranker（Cross-Encoder）？](https://github.com/lihe/MyGitBlog/issues/43)

下面我按“**面试能讲清 + 工程能落地**”的标准，把 **Reranker（Cross-Encoder）** 讲透：它是什么、怎么打分、怎么训练、怎么接入检索/RAG、为什么更准但更慢、以及常见坑和优化。



------





## **1）它到底是什么：从“召回”到“精排”**





现代检索 / RAG 基本是两阶段：



1. **召回（Recall）**：BM25 / 向量检索（Dual-Encoder）从海量文档里快速捞出 Top-K（比如 50~200）
2. **重排（Rerank）**：Cross-Encoder 对这 Top-K 做更精细的相关性判断，输出 Top-N（比如 5~20）





为什么要分两段？

因为 Cross-Encoder 很准，但无法对百万级候选逐一打分（太慢），所以只用于“候选集精排”。



------





## **2）Cross-Encoder vs Dual-Encoder：关键差别**







### **Dual-Encoder（向量检索）怎么做**





- query 和 doc **分别编码**成向量
- 相似度用 dot/cosine





$s(q,d)=\langle f(q), g(d)\rangle$



优点：doc 向量可离线预计算 → 检索超快

缺点：q 和 d **没有 token 级交互** → 细粒度匹配不够





### **Cross-Encoder（Reranker）怎么做**





- 把 query 和 doc **拼在一起**输入同一个 Transformer
- 让它做 **跨序列注意力交互**
- 输出一个相关性分数





输入格式（典型）：

```
[CLS] query tokens [SEP] doc tokens [SEP]
```

输出：



- 用 [CLS] 向量接一个线性层得到 score
- 或直接输出 “相关 / 不相关”的概率





优点：token 级交互 → 对词对齐、否定、数字、实体等特别敏感 → **更准**

缺点：每个 (q,d) 都要跑一遍 Transformer → **更慢、更贵**



一句话：



> Dual-Encoder 负责“海选”，Cross-Encoder 负责“面试”。



------





## **3）Cross-Encoder 的打分原理：它在学什么？**





它学的是一个函数：



$s(q,d)=\text{CrossEnc}([q;d])$



这不是向量相似度，而是模型直接“读完 query 和 doc”后判断相关性。

它擅长处理 Dual-Encoder 常见的痛点：



- **精确约束**：时间、地点、版本号、范围条件
- **否定与转折**：not / except / but
- **多条件组合**：同时满足 A、B、C
- **实体消歧**：Apple 公司 vs 苹果水果
- **长文证据**：看哪段真正能回答问题





所以你会看到：很多系统里 rerank 一加，RAG 幻觉明显降低。



------





## **4）训练方式：Cross-Encoder 怎么被训练出来的？**





训练数据通常是三元组或成对样本：





### **4.1 Pairwise（更常见）**





给定同一个 query：



- 正例文档 $d^+$（相关）
- 负例文档 $d^-$（不相关）





希望：

$s(q,d^+) > s(q,d^-)$



常用损失：



- **Margin Ranking Loss**
- **Pairwise Logistic Loss**（把差值过 sigmoid）
- 或者 softmax over candidates（Listwise）







### **4.2 Pointwise**





直接把 $(q,d)$ 标注为相关/不相关，做二分类（BCE / CE）。

优点：简单

缺点：相对排序学习能力弱一些（很多检索场景更关心“谁更相关”）





### **4.3 负例怎么采样（非常关键）**





- **Random negatives**：太容易，提升有限

- **Hard negatives**：从 BM25 / embedding 召回的“看起来相关但其实不对”的文档

  

  - 这是 reranker 能变强的关键

  





------





## **5）在 RAG / 搜索系统中怎么用：典型链路**





一个典型落地方案：



1. BM25 召回 Top-K1（比如 200）
2. 向量检索（BGE-M3 等）召回 Top-K2（比如 200）
3. 合并去重 → 候选集（比如 200~400）
4. Cross-Encoder rerank 候选集 → Top-N（比如 10）
5. Top-N 切 chunk / 拼证据 → 交给 LLM 生成答案





你会在工程上看到一个常用参数：



- **K**（rerank 的候选数）越大越准，但越慢
- **N**（最终给 LLM 的文档数）过大可能引入噪声、变慢、增加幻觉





------





## **6）为什么 Cross-Encoder 更准但更慢：复杂度直觉**





- Dual-Encoder：一次 query 编码 + 向量相似度扫描（ANN）
- Cross-Encoder：对每个候选都要跑一次 Transformer





如果候选 K=200：

就要做 200 次前向推理（哪怕是小 reranker 也很贵）。



所以一般策略是：



> 用小模型（reranker-base）跑 50~200；

> 或用更强 reranker 跑更小 K。

## **7）常见模型家族（你面试能说出来的那种）**





- **BGE Reranker**（如 bge-reranker-base/large）：中文/英文都常用
- **Cross-Encoder MS-MARCO 系列**（经典英文检索 reranker）
- **MonoT5**：把“相关性判断”当成生成任务做（速度更慢，效果可能强）
- **ColBERT**：介于 dense 和 cross 之间（token-level late interaction），速度/效果折中





（你在回答时不一定要背型号，讲清“Cross-Encoder 类 reranker”即可。）

## **8）工程落地要点（非常实用）**







### **8.1 输入长度与 chunk 策略**





Cross-Encoder 有最大长度限制（例如 512/1024 tokens）。

文档过长怎么办？



- 先把 doc 切 chunk
- rerank 的对象是 chunk（而不是整篇）
- 最终把 top chunks 送入 LLM







### **8.2 分数不可跨 query 比较**





reranker 分数通常只对**同一个 query 内排序**有意义，跨 query 的绝对值别过度解读。





### **8.3 延迟优化**





- 只 rerank Top-K（50~100 通常是甜点）
- 批处理（batching）把多个 (q,d) 一起推理
- 使用更轻量的 reranker 或 INT8 量化推理
- 缓存：对高频 query / 热门 doc 组合缓存打分







### **8.4 什么时候 reranker “不值”**





- 文档量很小（几十条）时：直接 cross-encoder 全量也行
- 查询极短、关键词非常明确：BM25 已经够好
- 你的系统对延迟极敏感：可能要降低 K 或改用轻量 reranker





------





## **9）面试级回答模板（你可以直接背）**





> Reranker 通常采用 Cross-Encoder 架构，将 query 与候选文档拼接后输入同一个 Transformer，通过 token-level 交互输出相关性分数。它用于两阶段检索的第二阶段：第一阶段用 BM25/向量检索快速召回 Top-K，第二阶段用 Cross-Encoder 对 Top-K 精排得到 Top-N。相比 Dual-Encoder，Cross-Encoder 更准确，尤其擅长处理多条件、否定、数字与实体匹配，但计算开销更大，因此只对候选集使用，并常配合 chunk、batching 与量化优化延迟。
